WHAT CHANGED, HOW IT WORKS, AND WHY IT MATTERS

1. Complete import verification
   Sources: rsoul/import_identity.py, rsoul/import_transaction.py

What: An import is recorded as successful only when all selected inputs
have proven outputs attached to the intended book record.
How: Save the intended author/work identity and medium, every input's
size and SHA-256 digest, local/server paths, pre-import bookfile IDs, and
the exact command. Correlate each input through exact source/output
history, or compare hashes of readable library output files. A partial
result remains pending or requires review.
Why: The older log's command-level "successful" result does not by itself
prove that every chapter imported, or that the files were attached to the
right record. A new file ID, an equal file count, or an empty staging
folder is not enough evidence.

2. Conversion coverage without requiring equal file counts
   Sources: rsoul/import_identity.py

What: A multi-MP3 book can correctly become one M4B.
How: Accept conversion history only when it links every staged input to a
committed output and that output's record, path and size agree. Preserve
partial or unverified outcomes when only some inputs have coverage.
Why: Requiring one output per input rejects legitimate conversion;
accepting any new output conceals missing chapters. Coverage establishes
the actual relationship instead of guessing from the number of files.

3. Stable book identity and compatible edition selection
   Sources: rsoul/import_identity.py, rsoul/import_transaction.py

What: Targeted import remains tied to the intended work, author and
medium, even after catalog edits. The Chaptarr edition compatibility
behavior carried forward from the intervening fixes is preserved.
How: Recheck saved identity/provider evidence before submission and
verification. Prefer an unambiguous edition of the right medium. Retain
the conservative provider-edition fallback for explicitly audiobook
records without usable audio-edition metadata. Missing editionId in a
bookfile response does not invalidate otherwise complete identity/output
proof; an explicit contradiction does. Targeted mode never silently
falls back to a folder scan.
Why: Numeric record IDs and descriptive tags are not sufficient work
identity. Conversely, incomplete provider edition fields should not
permanently block an otherwise provable correct import.

4. Durable operation intent, staging and state writes
   Sources: rsoul/import_transaction.py, rsoul/state.py,
            rsoul/persistence.py, rsoul/locking.py

What: Download/import work is journaled before mutations, and interrupted
work can resume without overwriting an unrelated file.
How: Save intent before enqueue/import requests and receipts afterwards.
Stage in unique operation directories using replayable per-file moves.
Checkpoint with unique temporary files, flush/fsync and atomic replace.
Serialize state changes and require the application's instance lock.
Damaged state or a failed durable write stops further unsafe mutations;
foreground processing observes background persistence errors too.
Why: A restart must not erase evidence that a server accepted work, turn a
bad state file into an empty queue, or allow two instances to reuse the
same file ownership. Keep the real persistent data mount: a different
writable directory at the same path is not detectable from these checks.

5. Ambiguous API responses are reconciled before retry
   Sources: rsoul/backends/slskd_backend.py, rsoul/import_transaction.py

What: A lost response does not become permission for an immediate repeat
of an enqueue or import.
How: Reconcile uncertain slskd enqueueing against exact owned transfer
evidence. Save an import's submission attempt before POST. A lost import
receipt stays submission_unknown with its original request and baseline;
it does not trigger a blind second POST. Legacy no-receipt imports remain
ambiguous even when their old submission counter is zero.
Why: The server may have accepted an operation before the connection
failed. Repeating it can create duplicate transfers or imports and make
the original outcome harder to establish.

6. Download completeness survives restart and cleared transfer rows
   Sources: rsoul/backends/slskd_backend.py, rsoul/download.py,
            rsoul/orchestrator.py, rsoul/state.py

What: A complete download requires every expected local file and its
known byte size, both during live monitoring and after restart.
How: Keep an immutable selected manifest separate from mutable transfer
status. Require regular files of the expected sizes, with a configurable
settling interval for slskd's final rename. Clearing completed transfer
rows cannot shrink the original expected file inventory. Legacy tasks
without sufficient size/identity evidence are retained for review.
Why: "Completed", one visible chapter, a placeholder, a short file, or a
directory named like an audio file does not establish a complete book.
This also makes a 136-part audiobook remain a 136-part obligation across
monitor-window handoffs.

7. Scoped transfer cleanup and retired-attempt ownership
   Sources: rsoul/backends/slskd_backend.py, rsoul/workflow.py

What: Cleanup cannot intentionally remove another application's transfers
or reuse an old attempt's ownership to remove a replacement download.
How: Operate on owned transfer IDs and recorded local files. Require
confirmed remote cleanup before local cleanup/retry. Journal local moves
and retired-attempt status. Retain ownership when cleanup is uncertain;
keep files when a remote import may still be using them.
Why: Shared author folders and retries make broad name-based cleanup
unsafe. A failed cleanup request is not proof that nothing is running.

8. Correct audiobook grouping and format coverage
   Sources: rsoul/match.py, rsoul/backends/slskd_backend.py

What: Small wanted files cannot pull in a larger sibling work, and a
preferred extension cannot hide missing parts of a mixed-format book.
How: Group using work/title evidence and the known author bibliography
before applying size or format preference. Browse full candidate
directories; check relevant numbered coverage before selecting a format.
A separately complete recording with different legitimate chapter
boundaries can still be chosen. Keep distinct directories from the same
peer as candidates through evaluation.
Why: An author folder may contain several books. Size and extension are
not work identity. Rejecting one directory should not hide another valid
copy from the same peer.

9. Long numbered sets and fragment detection
   Sources: rsoul/match.py, rsoul/audiotags.py,
            rsoul/import_transaction.py

What: Check numbered chapters beyond 99 and retain evidence of samples,
previews, excerpts and prologue-only releases through matching/recovery.
How: Bounded numbering logic supports up to 10,000 parts, checking clear
starts, gaps and totals while allowing recognized disc layouts. Inspect
raw labels before normalization and recheck the complete selected set
before import. Preserve original peer-folder labels in recovered work.
Allow a full book containing a prologue chapter, actual titles containing
such words, and supported named short stories within collections.
Why: Normalizing away "prologue" must not make an extract look complete.
A blanket ban on every such word would reject valid titles. Mixed or
ambiguous numbering remains inconclusive rather than proof of completeness.

10. Inspect every audio file, with recording policies
    Sources: rsoul/audiotags.py, rsoul/recording_policy.py,
             rsoul/import_transaction.py

What: Validate every selected audio file, distinguishing untagged but
valid audio from corrupt bytes or tags without a usable stream.
How: Mutagen checks stream/container/codec information and positive
duration. Compare title tags with the intended work and catalog siblings;
an album naming the wanted book does not erase a contradictory track.
Optional language, narrator, abridgement, Booktrack and dramatization
policies use actual candidate/download metadata. Unknown evidence follows
the configured allow/warn/reject policy. Title-check warn/off does not
bypass stream integrity or explicitly configured recording restrictions.
Why: Sampling a few chapters misses corrupt or contradictory files
elsewhere. Catalog descriptions do not prove which performance was
actually downloaded. Structural inspection is not full audio decoding,
transcription or a guarantee of every spoken chapter's presence.

11. Narrator-based edition selection uses complete identities
    Sources: rsoul/import_identity.py, rsoul/import_transaction.py

What: Fix the uploaded tie-breaker that could choose Jane Porter's edition
from Ray Porter tags because both contained the surname Porter.
How: Parse only text, including nested tag lists. Normalize Unicode and
explicit surname/given-name inversion, without turning surnames into
independent matching fragments or splitting a scalar string into letters.
Require all known complete downloaded narrator identities to be present
in exactly one eligible edition. Preserve name order unless a comma
explicitly marks inversion. Do not guess missing name parts or initials.
A unique monitored edition retains its existing priority. Ambiguous comma-only
fields containing multiple words on both sides supply no tie-break evidence;
use separate tag values or explicit cast separators to disambiguate.
Why: A narrator is a person, not a shared surname. Ray Porter can match
Porter, Ray; it cannot match Porter, Jane or Porter alone. Ambiguous casts
and ties remain unresolved. Narrator evidence cannot select another
medium or silently replace the user's unique monitored-edition choice.

12. Configurable size/bitrate and optional runtime checks
    Sources: rsoul/backends/slskd_backend.py,
             rsoul/import_transaction.py, rsoul/config.py, config.ini

What: Preserve the uploaded configurable bitrate floor and runtime
comparison, with validated numeric settings.
How: audiobook_min_bitrate_kbps defaults to 8; zero disables this check.
It compares candidate size with a known catalog duration. The independent
candidate total-size threshold still applies. audiobook_duration_tolerance
defaults to zero/off; when enabled, compare validated total downloaded
duration with available catalog runtime and retain excessive drift for
review. A value of 0.25 permits 25 percent drift. Off means no extra
runtime lookup. Reject negative, nonfinite or invalid configuration.
Why: Small complete recordings need a configurable threshold; an optional
runtime check can expose incomplete or different performances. Runtime
can vary between editions, so it is not a default completeness guarantee.

13. Catalog outages preserve strict identity checks
    Sources: rsoul/library.py, rsoul/backends/slskd_backend.py,
             rsoul/import_transaction.py

What: Unavailable catalog evidence is distinct from a valid empty
bibliography or genuinely missing tags.
How: Known-author audiobook search requires a valid author bibliography.
Default reject-mode title validation waits when the needed catalog is
unavailable. Malformed/failing responses are not cached as successful
empty lists; valid empty responses remain distinguishable.
Why: Losing sibling-work evidence during an outage must not make the
wrong book acceptable or turn a service error into "not found".

14. Rate limits, search pacing and useful query fallbacks
    Sources: rsoul/search_control.py, rsoul/search.py,
             rsoul/outcomes.py, readarr_api/request_handler.py,
             rsoul/backends/slskd_backend.py

What: Separate a completed no-match search from HTTP 429, service errors,
incomplete searches, incomplete browsing and uncertain enqueueing.
How: Preserve HTTP status/Retry-After evidence. Share and persist pacing
and backoff across books/runs. Accept Retry-After seconds or HTTP dates;
use bounded fallback/jitter when needed. A server delay longer than the
configured per-wait budget is retained and defers work. Queries keep the
author surname and distinctive title terms within a per-book budget.
Why: The logged 429 is a service refusal, not proof that Endeavour is
unavailable. A first-name-only query such as "Christopher - The War"
adds noise. Immediate repeated requests make rate limits worse.

15. Retry classification and scoped source history
    Sources: rsoul/history.py, rsoul/ledger.py, rsoul/orchestrator.py,
             rsoul/backends/slskd_backend.py, rsoul/workflow.py

What: Definite peer refusal, unavailable content, local import trouble
and service outages retain different meanings.
How: Only a completed negative search receives the normal not-found
cooldown. A confirmed asynchronous peer rejection can try another retained
candidate within the attempt budget after owned cleanup. Failure history
is scoped by backend, author, work, medium, release and reason. Preserve
old unscoped entries without applying them as new scoped bans.
Why: The logged Completed, Rejected result for Winter's Heart was not a
successful search with no matches. Local permission/path/API/import faults
should not ban a peer or a same-title ebook or different release.

16. Wanted backlog, duplicates and active-download limits
    Sources: rsoul/wanted_queue.py, rsoul/library.py, rsoul/workflow.py

What: Duplicate records, exclusions, cooldowns and a full transfer queue
cannot silently consume or discard the rest of a wanted page.
How: Check eligibility before limiting attempts/active downloads. Save
unattempted candidates and the page cursor together. Keep saved work when
a wanted endpoint fails and allow other healthy sources to continue.
Handle media filtering for supported records lacking explicit fields.
Poll transfers between searches and during pacing waits.
Why: The duplicate Temporal Void and other records in the logs used
attention and slots without representing new books to fetch. A queue cap
should delay remaining work, not make it disappear.

17. Real workflow import coordination
    Sources: rsoul/workflow.py, rsoul/postprocess.py

What: Fix the uploaded implementation whose synthetic batch helper worked
but whose production single-item callback still waited for each import
before submitting the next.
How: One coordinator serializes import state mutations. It submits queued
completed downloads without polling to completion, then checks accepted
operations against their own fixed per-run deadlines. New completions
wake the coordinator and can be submitted while older commands wait.
Completion, cleanup and summary updates remain serialized. End-of-run
waiting, health heartbeats, disable_sync, and fatal checkpoint propagation
remain connected to the actual workflow.
Why: A slow Chaptarr import should not hold later completed downloads
behind its entire poll timeout. This avoids parallel mutation races while
allowing several accepted server-side imports to be followed together.
Synchronous API calls and file validation still take time; this is not an
unbounded parallel import executor.

18. Explicit legacy recovery and strict command evidence
    Sources: rsoul/recover.py, rsoul/import_transaction.py

What: Provide an explicit per-book recovery path for eligible legacy
imports, and restore the stricter guards weakened in the uploaded version.
How: Inspection combines saved inventory with live commands, history and
bookfiles. --apply requires the instance lock, one book, coherent local
inventory, original known sizes, usable paths and no blocking evidence.
It archives the old decision and creates a fresh validating transaction;
the normal worker then validates, stages, submits and verifies.
Command names must be nonempty strings. A relevant ManualImport needs a
nonempty files list with usable absolute paths on every entry. A scan
needs its actual absolute path. NULs, invalid paths, malformed entries and
unreadable API responses block a decision rather than looking unrelated.
Why: An absent receipt or incomplete command body cannot establish that
nothing was imported or is still reading the files. The recovery command
itself does not submit an import or bypass normal validation.

19. Recovery distinguishes completed from unsuccessful
    Sources: rsoul/recover.py

What: Completion alone cannot authorize a second attempt or discard.
How: A matching completed command must explicitly report unsuccessful to
establish failure. Missing/empty/unknown results block; successful blocks.
Explicit failed/aborted/cancelled/orphaned statuses permit terminal-failure
handling only with empty or explicit unsuccessful results. Unknown
nonempty outcomes, including failed/result=unknown, remain blocking.
Other inventory, path and history checks must also pass.
Why: Lifecycle completion does not describe file import success. Treating
unknown outcomes as failure can duplicate a successful import or move its
files away. This intentionally restores conservative behavior.

20. Correct path overlap on POSIX and Windows
    Sources: rsoul/recover.py

What: Parent-directory scans and case-varied Windows targets correctly
count as overlapping import work.
How: Compare normalized path components, not string prefixes. Recursive
scans overlap in both ancestry directions. ManualImport retains its exact
file scope. Preserve drive-root qualification and case-fold drive/UNC
paths appropriately; require an actual UNC share or drive-qualified path.
Root-relative Windows paths remain inconclusive. Reject NUL-containing
paths before comparing them.
Why: C:\ can scan a saved book below C:\Media\Downloads, and a differently
cased UNC spelling can refer to the same target. Conversely, book and
book-other are not the same directory. Missing overlap must not authorize
file movement or another import.

21. Discard checks actual file ownership and all relevant mappings
    Sources: rsoul/recover.py

What: Fix both destructive discard errors found in the uploaded version:
missing an active import at the unstaged source, and moving a later task's
replacement file from an old source path.
How: Build a per-file discard plan from actual current locations. Inspect
saved and current local/server mappings and relevant staging/source paths
against live evidence. Compare current ownership and file identity before
claiming a file. A historical source location is not an ongoing ownership
claim once that input is staged elsewhere. A damaged file in an exclusively
owned stage can still be deliberately discarded when the other evidence
is clear; uncertainty remains blocked.
Why: Planned staging paths do not describe a validating transaction's
actual files. Shared source directories can be reused. A manual discard
must not move another task's bytes or files an active import is using.

22. Discard is journaled before file movement
    Sources: rsoul/recover.py, rsoul/workflow.py,
             rsoul/import_transaction.py, rsoul/postprocess.py

What: An interrupted --discard is recoverable, including partial moves
and failure to remove the final saved task.
How: Record exact per-file quarantine destinations and current-byte
identity in durable task state before moving anything. Keep the decision
archive. On retry, reconcile source/destination presence and identity;
refuse unexpected replacements or conflicts. Retain the journal until
file handling and task retirement complete. Normal import, download
resume, startup cleanup and retention recognize unfinished discards and
leave them to explicit recovery. Error messages acknowledge when a
checkpoint or move may already have happened.
Why: A generic "nothing changed" after a failed second move is false.
Without the durable destination map, restart can lose track of the first
moved file or try to import the remaining half of an intentionally
discarded book. Discard quarantines owned local files; it does not delete
Chaptarr library records or prove a new download is desirable.

23. Retention reads structured ownership, including Unicode paths
    Sources: rsoul/postprocess.py

What: Fix deletion of still-owned folders whose names were escaped by
JSON serialization, such as Die Flüsse von London, quoted names and
backslashes. Retention remains opt-in.
How: Read structured saved path fields, normalize their components and
check containing/contained paths. Include recovery/discard destinations
and legacy state. Recheck ownership under StateManager's lock immediately
before deletion. A configured download root alone does not own every
quarantine folder. Missing, unreadable, malformed, read-only or unavailable
state pauses retention. Preserve the quarantine-marker clock and symlink
checks; an old folder without a marker starts its clock when first seen.
Why: Searching serialized JSON for a raw path fails when escaping changes
its text. A retention job must not remove a file still needed for recovery.
Conversely, treating a mount root as ownership of all descendants would
silently make retention ineffective forever.

24. Bounded background notifications
    Sources: rsoul/notify.py, rsoul.py

What: Optional webhook delivery cannot hold import/state processing behind
a slow or trickling HTTP response.
How: Use one reusable daemon worker and a bounded queue of 32 notices.
Bound payload/URL sizes, capture each job's transport/configuration, use
socket timeouts, avoid response-body buffering and redirect following,
and close the response/connection. Shutdown gives outstanding notices one
shared bounded grace period, then drops queued work. A hung delivery does
not spawn replacement workers indefinitely or delay process exit.
Why: Requests' timeout is an inactivity timeout, not a total wall-clock
deadline. A server can trickle a response for much longer. Notifications
are best effort: queued does not mean delivered, delivery is not retried,
and a full queue or shutdown may drop notices. Core state remains the
source of truth.

25. Webhook secrecy and actual submission-unknown events
    Sources: rsoul/notify.py, rsoul/import_transaction.py, rsoul/config.py

What: Suppress webhook URL secrets in HTTP-library DEBUG output and emit
the previously missed submission_unknown notification for an actual
ambiguous POST outcome.
How: Keep startup redaction and filter Requests/urllib3 logging only on
the delivery thread; log delivery status/type without exception URLs.
Keep the pre-POST submission_unknown checkpoint for duplicate prevention.
When the outcome actually becomes unknown, save the notification decision
once per unresolved attempt, then enqueue the enabled event. Polling the
same uncertainty does not repeatedly alert or submit another command.
Why: Webhook credentials often live in the URL path, which debug HTTP
logs expose even if application configuration logs are redacted. Also,
saving a safety phase before POST is not the same as announcing a failure;
the old phase-change check could suppress the real failure event entirely.

26. Clear cross-filesystem staging failures
    Sources: rsoul/import_transaction.py

What: Preserve the useful EXDEV diagnosis without promising an automatic
retry for a review-required transaction.
How: Explain that source and stage must be on the same filesystem for
the protected rename path, keep the journal/files for review, and describe
that correcting a mount alone does not advance a needs_review record.
Why: A generic move error obscures a deployment problem. Silently copying
across mounts changes crash/ownership guarantees. Recovery instructions
must match the actual phase, rather than imply restart will resubmit.

27. Operator visibility, exclusions, paused imports and dry run
    Sources: rsoul/diagnostics.py, rsoul/health.py, rsoul/display.py,
             rsoul/workflow.py, rsoul.py, config.ini

What: Version/build, state diagnostics and run summaries describe the
actual task phase and verified outcome. Operator controls remain explicit.
How: Report per-book files/bytes/peer/queue progress and timeout context;
distinguish failed transfers, pending/review imports, verified completion
and cleanup. Read-only diagnostics uses central state with no API calls
or migration. disable_sync pauses new and pending import submissions.
Local ID/title/publication-type exclusions do not delete catalog records
or change monitoring. remove_wanted_on_failure remains False in the
sample. Dry run reports search candidates without enqueue/import or normal
cursor/recovery mutation, while still consuming normal search API budget.
Why: Repeated "Active: 1" is not enough to diagnose a long peer queue.
The duplicate/graphic-adaptation/series records in the logs may be unwanted,
but software should not guess that every collection is an invalid target.

28. Cumulative packaging, documentation and meaningful regressions
    Sources: README.md, config.ini, Dockerfile, .dockerignore,
             APPLY_V11_FROM_GITHUB.txt, V11_NOTES.md, V11_VALIDATION.txt,
             tests/

What: Deliver the complete implementation from the pinned GitHub baseline
under one v11 identity, with current instructions and validation evidence.
How: Replace contradictory draft release/version/test claims, document
actual defaults and recovery semantics, retain the application build/CI
support, include valid audio fixtures and tests that exercise the real
workflow, state persistence and recovery entry points. Check the cumulative
patch through both git apply and git am in clean baseline checkouts and
compare every tracked file and executable mode with the release tree.
Why: A test of an isolated helper can miss an unused production path.
A patch against v10.4 is not the correct deliverable for an installation
still based on the live GitHub revision identified in this conversation.
Restarting an old image is not installation of the patched source.

    audiobook_tag_check = reject
    failed_retention_days = 0

permits permanent removal of sufficiently old, unreferenced quarantine
folders; operator-discard archives remain in the data directory. Runtime
comparison remains off by default. Notification queue bounds and the shared
shutdown grace period are implementation limits, not extra config knobs.

UPGRADE FROM THE PINNED GITHUB REVISION

1. Prepare an isolated source checkout.

If your existing checkout has local edits or another revision, preserve it
and use a separate checkout of the exact base. Do not reset or overwrite
local work to force the patch. A fresh clone may be prepared with:

    git clone --branch audiobook-support https://github.com/HariOcto/rsoul.git rsoul-v11
    cd rsoul-v11
    git switch --detach 612a90e5e32f6250c9c7b77d8a6a84278e815e5b

Verify the revision and that there are no local changes:

    git rev-parse HEAD
    git status --short

Then apply this completed patch using its real downloaded path:

    git apply --check /path/to/rsoul-github-to-v11.patch
    git apply /path/to/rsoul-github-to-v11.patch

Alternatively, after git apply --check, use git am on the same file to
create one commit. Do not run both git apply and git am. Do not force
rejected hunks or layer this over an earlier v11 patch.

2. Validate source and build an image.

In a Python 3.11 or 3.12 virtual environment:

    python -m pip install -r requirements-dev.txt
    python -m pytest -q tests
    bash -n run.sh
    python rsoul.py --version

Expected version output:

    R:soul 11 (v11)

From the patched source on a Docker-capable build host:

    docker build -t rsoul:v11 .

Make that image available to the TrueNAS/deployment host and select it in
the application's configuration. The sample Compose service selects an
image and has no build entry: point it at your built image. Pulling an
unrelated latest tag or restarting the existing container does not install
this patch. Actual local test results and untested deployment boundaries
are recorded in V11_VALIDATION.txt.

3. Preserve runtime data during the cutover.

Stop the old rsoul instance. Back up its actual persistent /data contents
while stopped and retain downloaded files and sidecar journals. Preserve
URLs, API keys, runtime UID/permissions, and completed-download mounts.
Start exactly one instance using the new image and the same data. Do not
clear state or run old/new instances together to force a clean startup.

For the setup in the supplied logs, preserve these settings if both paths
still name the same physical files from their respective containers:

    RSOUL__READARR__IMPORT_METHOD=targeted
    RSOUL__SLSKD__DOWNLOAD_DIR=/downloads
    RSOUL__SLSKD__READARR_DOWNLOAD_DIR=/downloads/slskd/downloads
    RSOUL__SEARCH_SETTINGS__MEDIA_MODE=audiobook
    RSOUL__SEARCH_SETTINGS__REMOVE_WANTED_ON_FAILURE=False
    RSOUL__DOWNLOAD_SETTINGS__MAX_ACTIVE_DOWNLOADS=10
    RSOUL__DOWNLOAD_SETTINGS__MONITOR_WINDOW=1800
    RSOUL__DOWNLOAD_SETTINGS__QUEUE_TIMEOUT=7200
    SCRIPT_INTERVAL=300

The different container paths are expected. They should not be made equal
just because their strings differ. The supplied timing overrides preserve
your logged behavior; they are different from some sample defaults.

4. Verify the running deployment.

Inside the newly running container:

    python /app/rsoul.py --version
    python -m rsoul.diagnostics --config-dir /data

Confirm the v11 build, actual mounts, writable state, and intended
book associations for representative imports. A monitor-window handoff
means work remains active for a later run; it is not an import success.

RECOVERY AND DISCARD

A. Inspect saved work.

Use the same image/runtime, environment, UID, configuration and mounts as
the normal application:

    python -m rsoul.diagnostics --config-dir /data
    python -m rsoul.recover --config-dir /data
    python -m rsoul.recover --config-dir /data --book YOUR_BOOK_ID

Replace YOUR_BOOK_ID with an actual numeric ID. Diagnostics reads central
state only; it does not query services or scan sidecars. Recovery inspection
also reads live command/history/bookfile evidence. It does not post an
import or move files. Inspect local/server mappings, every retained file,
command status/result and the displayed blocking reasons.

B. Apply an eligible legacy recovery decision.

Stop the normal instance and back up state first. In a one-off runtime
with identical settings/mounts, run:

    python -m rsoul.recover --config-dir /data --book YOUR_BOOK_ID --apply

For a Compose service named rsoul already configured with this image:

    docker compose run --rm --no-deps --entrypoint python rsoul -m rsoul.recover --config-dir /data --book YOUR_BOOK_ID --apply

This requires the normal service to be stopped. A stopped container cannot
be entered with docker exec. Use the corresponding maintenance runtime in
TrueNAS if that is how the app is managed.

--apply repeats the evidence checks under the application lock. It archives
the old record/decision and creates a fresh validating transaction. It does
not move input files or POST an import. Restart the normal worker to run
validation, staging, submission and verification. Bad audio, contradictory
identity, fragments, incompatible recording policies or unavailable catalog
evidence can still prevent import. This is an explicit legacy recovery
path, not a universal retry switch for every needs_review operation.

C. Discard an eligible retained import when that is your decision.

With the normal instance stopped and the same runtime settings:

    python -m rsoul.recover --config-dir /data --book YOUR_BOOK_ID --discard

--discard is separate from --apply; they cannot be combined. It refuses
running downloads/imports and ambiguous live evidence. It moves only the
validated owned local files into quarantine and retires the saved task
when the operation completes. It archives the decision in
recover_archive.jsonl and records the in-progress operation in task state.
It does not delete a library book or automatically fix its wanted status.

If discard is interrupted, inspect the retained operator_discard journal
and rerun the same per-book --discard after resolving the reported cause.
Do not manually clear the journal to make normal imports resume: some files
may already be quarantined. Reconciliation verifies current source and
exact destination identity before continuing. Changed mappings or conflicting
ownership can block continuation and require an explicit operator review.

Correcting a mount or permissions on a needs_review transaction does not
itself resubmit it. The recovery output describes whether apply or discard
is eligible; uncertain server outcomes remain protected.

ADDENDUM (23 November 2026): WRONG-AUTHOR MATCHES

The first live v11 run imported a dance track as Ryk Brown's "Resistance": the
14 MB file "01 Resistance (JTS Mix).mp3" from a folder "Scott Brown\Hardcore
Tracks". Three checks are tightened:

- The author's surname must belong to the author. In each path segment, a
  different given name right before the surname ("Scott Brown", "James
  Brown") or after a comma ("Brown, Scott") makes that mention another person.
  Initials count only when they are the author's. One-name authors are
  unaffected. This applies to folder and file matches alike.
- An artist or album-artist tag naming another person with the author's
  surname is a confirmed mismatch, unless another credit names the author.
  Artist tags naming neither (often the narrator) remain neutral.
- [Search Settings] audiobook_min_duration_minutes (default 15, 0 = off): files
  that play for less than this in total are set aside for review, not imported.

The same run also queued tacica's album "singularity" (12 songs, about 45
minutes) for Ryk Brown's "Singularity": the search "Brown - Singularity" found
it because one song's name contains "Brown". Two more checks:

- Folders in a music library (a path segment such as Music, Musique, Música,
  OST or Soundtracks) are skipped unless the path also marks spoken word
  (Audio Books, Audiobooks, Hörbücher, Spoken Word ...).
- A file name only stands in for the author when it names the book as well
  ("Ryk Brown - Singularity.m4b"); otherwise the author must be in the folder
  path.

The underlying rule, after looking at why both got through: a title match plus
the author's surname somewhere in the path was treated as enough, but Soulseek
matches words anywhere in a path, so "Brown - Resistance" returns every song
called Resistance by anyone called Brown. A wrong book costs a manual clean-up;
a skipped one is only searched again later. So:

- Every candidate now needs positive evidence that it is this author's
  audiobook: the author named in full ("Ryk Brown", "Brown, Ryk", "C. Nuttall"),
  a spoken-word folder or file name (Audiobooks, Audio Books, Hörbücher,
  Unabridged, read by, Libation, Audible ...), an audiobook container (m4b), or
  a narrator Chaptarr lists. Every correct pick in the November logs has such
  evidence; none of the wrong ones has.
- Fallback queries keep at least two distinctive title words ("Brown - First"
  and "Brown - my Enemy" are no longer sent); a one-word title is searched
  with the full author name and "Surname - Title" only.
- The same checks run again before import, on the peer's folder, so a download
  queued before this change or resumed from saved state is held for review.

After an outside review of that change:

- Person names are read as a whole, within one field (a path segment, or one
  side of " - "): a mention is the author in full (first name or its initial
  with the surname), the surname alone, a listed narrator, or another person
  (a given name or initial the author doesn't have: "Scott Brown", "Michael F.
  Hamilton", "Anne Le Guin"). Another person rules a candidate out unless the
  same path names the author in full; a bare surname never outweighs it.
  Surname particles ("Le Guin") belong to the surname, and the book's own title
  words are never read as a given name ("Resistance - Brown").
- Search and import make the same evidence decision with the same inputs,
  including the narrators Chaptarr lists (fetched before import only when
  nothing else shows the evidence; an unreadable catalog defers the import).
- Artist credits are judged per file, with every value of multi-value tags; a
  listed narrator sharing the surname is not another author.
- Unsubmitted work staged under older rules is validated again, on the files
  it owns, before it is moved further or submitted (validation_policy in the
  saved transaction). Submitted or uncertain imports are only reconciled.
- A music folder no longer vetoes on its own: the author named in full plus an
  m4b or a listed narrator still qualifies. Folder words match whole words.
- Fallback queries may drop an article ("Tolkien - Hobbit"); the rule that two
  meaningful words remain applies only when meaningful words are dropped.
- Edit book_ledger.json only while R:soul is stopped: a running R:soul keeps it
  in memory and would write the old entry back.

A book already imported wrongly is not undone: delete its file in Chaptarr and
its entry in book_ledger.json, so the book is wanted and searched again.

Full suite after this change: 1,284 tests passed.
